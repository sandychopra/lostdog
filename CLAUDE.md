# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Lost Dog and Cat Rescue Foundation shift-report app. Full product scope, data model, and feature list live in `project-scope.md` — read it before implementing any feature-level work, since the domain rules (cat/kennel/group state transitions, announcement resolution rules, checklist ordering, etc.) are detailed and easy to get subtly wrong from guessing.

The intended tech stack is documented in `Tech-Stack.md` (Postgres + Prisma, database-backed sessions for auth, S3-compatible photo storage, SendGrid for email, Docker deployment) and the build order is documented in `implementation-plan.md`, organized into phases with the reasoning for why phases are sequenced that way. **Phase 0 (foundations), Phase 1 (data model), and Phase 2 (auth & user management) are done.** Phase 2, via Better Auth: login, database-backed sessions, role-gated routes, and full admin user CRUD (create/list/edit/soft-delete) all work end to end. Phase 1: the full roster/shift-report/announcement schema (`Cat`, `Group`, `Litter`, `Kennel`, `ShiftReport`, `CatEntry`, `GroupEntryCatDetail`, `Photo`, `MeetAndGreet`, `KennelPrepChecklist`, `ChecklistAction`, `Announcement`, `SignTask`, `KennelMoveRequest`, plus join tables) exists and is migrated, with representative seed data — see `backend/prisma/ERD.md` for the current entity-relationship diagram (auto-regenerated by `prisma generate`, see `backend/prisma/schema.prisma`'s `erd` generator). None of Phase 3+'s actual CRUD/business logic is implemented yet — the schema exists, but there's no roster management, shift reports, announcements, or reporting UI/API. Check `implementation-plan.md`'s checkboxes for current per-item status rather than assuming phase boundaries are clean.

## Commands

This is a Bun workspace monorepo (`backend/`, `frontend/`), not npm/yarn/pnpm.

```bash
bun install                # install all workspace deps, from repo root

bun run dev:backend &       # start the Express API with watch mode (http://localhost:4000)
bun run dev:frontend &      # start the React dev server with HMR (http://localhost:3000)


kill $(lsof -t -i :4000)   # backend
kill $(lsof -t -i :3000)   # frontend
```

Each can also be run directly from its own directory: `cd backend && bun run dev`.

- Health status: frontend at `http://localhost:3000`, backend healthcheck at `http://localhost:4000/api/health`.

- `frontend` has a `build` script (`vite build`, producing static output in `frontend/dist/`, including the `vite-plugin-pwa`-generated service worker/manifest); `backend` has no build step since Bun runs the TypeScript directly (`bun src/index.ts`).
- `bun run lint` / `bun run format` / `bun run format:check` (from repo root) run ESLint/Prettier across both workspaces via the root `eslint.config.mjs` and `.prettierrc.json`. No typecheck script is configured yet.
- `frontend` has Bun-native tests (`*.test.tsx`, using `@testing-library/react`) but no `test` script wired up yet — run with `cd frontend && bun test`.

## Architecture

- **Monorepo**: Bun workspaces defined in the root `package.json` (`backend`, `frontend`). A shared `tsconfig.base.json` at the root holds Bun's recommended compiler options; each workspace's `tsconfig.json` extends it.
- **Backend** (`backend/src/index.ts`): a plain Express app run directly by the Bun runtime — no transpile/build step, no nodemon (Bun's own `--watch` flag handles reload). CORS is enabled since the frontend calls it from a different origin/port in dev.
- **Database schema** (`backend/prisma/schema.prisma`): `snake_case` columns via explicit `@map` (native Postgres convention) with `camelCase` in the Prisma schema/client (Prisma/JS convention) — applies to every table, including the Better Auth ones. `bunx prisma generate` regenerates both the Prisma client (`src/generated/prisma`, gitignored) and `backend/prisma/ERD.md`, a Mermaid entity-relationship diagram of the full schema (via the `erd` generator block, `prisma-erd-generator`) — check it after any schema change instead of re-deriving relationships by reading models one by one.
- **Frontend** (`frontend/src/`): React + TypeScript, bundled and hot-reloaded by **Vite** (`frontend/vite.config.ts`) — `@vitejs/plugin-react` for Fast Refresh, `@tailwindcss/vite` for Tailwind v4, and `vite-plugin-pwa` for the installable-app manifest/service worker (icons are still pending brand assets from the org, per `project-scope.md`'s Design/Branding section). The entrypoint is `frontend/index.html`, which loads `src/frontend.tsx`. Bun still runs the dev/build/test *commands* (`bun run dev` invokes the `vite` binary, `bun test` runs Bun's own test runner independently of Vite), but bundling itself is Vite's, not Bun's.
- The frontend calls the backend via an absolute URL from `PUBLIC_API_URL` in `frontend/.env`, exposed as `API_BASE` in `frontend/src/lib/config.ts`. Vite inlines `import.meta.env.PUBLIC_*` references into the browser bundle at build time (`envPrefix: "PUBLIC_"` in `vite.config.ts`), so changing the value needs a frontend restart/rebuild, and only `PUBLIC_`-prefixed vars ever reach the browser. There's no dev proxy configured, so CORS on the backend (`FRONTEND_URL`) is what makes this work locally.
- The backend and frontend aren't containerized; only Postgres is, via the root `docker-compose.yml` (`docker compose up -d postgres`), as an opt-in alternative to installing Postgres natively — see `post-pull-checklist.md`. `Tech-Stack.md` specifies Docker + a managed container platform for eventual production deployment, which is separate, later work (Phase 9).
