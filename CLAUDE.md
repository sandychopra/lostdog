## Project

Lost Dog and Cat Rescue Foundation shift-report app. Full product scope, data model, and feature list live in `docs/project-scope.md` — read it before implementing any feature-level work, since the domain rules (cat/kennel/group state transitions, announcement resolution rules, checklist ordering, etc.) are detailed and easy to get subtly wrong from guessing.

The intended tech stack is documented in `docs/tech-stack.md` (Postgres + Prisma, database-backed sessions for auth, S3-compatible photo storage, SendGrid for email, Docker deployment) and the build order is documented in `docs/implementation-plan.md`, organized into phases with the reasoning for why phases are sequenced that way. **Phases 0–7 are done: foundations, data model, auth & user management, cat/kennel roster, shift reports, status & announcements, and reporting & lookup.** Phase 2, via Better Auth: login, database-backed sessions, role-gated routes, and full admin user CRUD (create/list/edit/soft-delete) all work end to end. Phase 1: the full roster/shift-report/announcement schema (`Cat`, `Group`, `Litter`, `Kennel`, `ShiftReport`, `CatEntry`, `GroupEntryCatDetail`, `Photo`, `MeetAndGreet`, `KennelPrepChecklist`, `ChecklistAction`, `Announcement`, `SignTask`, `KennelMoveRequest`, plus join tables) exists and is migrated, with representative seed data — see `backend/prisma/ERD.md` for the current entity-relationship diagram (auto-regenerated by `prisma generate`, see `backend/prisma/schema.prisma`'s `erd` generator). Phase 3: full Cat/Kennel/Group/Litter roster CRUD, both backend and frontend. Phase 4: ShiftReport/CatEntry (individual + group variant)/MeetAndGreet CRUD, photo upload (local-disk storage in dev behind a small `PhotoStorage` interface — see `backend/src/lib/storage.ts` — swappable for Cloudflare R2 later), kennels-reset/kennels-flagged side effects on submit, and the probiotic-overdue roster indicator. Phase 5: structured Cat status transitions with Sign Task/Announcement side effects (`backend/src/lib/catStatus.ts`), Confirm Pickup, Kennel Move Requests (`backend/src/lib/kennelMoveRequests.ts`), Kennel Prep Checklists (`backend/src/lib/kennelPrepChecklists.ts`), and the Announcements feed (`AnnouncementsPage.tsx`) with its default-24h/unresolved view plus "view all". Phase 6: shift-report search filters, per-cat history (`/cats/:id`), kennel page (`/kennels/:id`), photo browse with Admin-only original/zip download (`archiver`), and an Admin-only `ActivityLog` audit trail for Cat/Kennel changes — every Cat/Kennel mutation must call `logActivity` (`backend/src/lib/activityLog.ts`) in its transaction. Phase 7: email notifications via a post-commit outbox — `flushPendingEmails` (`backend/src/lib/notifications.ts`) sends any unsent emailable Announcement/submitted ShiftReport through the `Mailer` interface (`mailer.ts`; SendGrid only when fully configured and never under `bun test`, else console), triggered by a middleware in `index.ts` after any successful non-GET plus a 5-minute retry loop; failures are stored on the row (`emailAttempts`/`emailLastError`). New Announcement types that should be emailed must be added to `EMAILED_ANNOUNCEMENT_TYPES` and `renderAnnouncementEmail` in `emailTemplates.ts`. Phase 8 (PWA & responsive polish) is code complete, pending real-device checks: every signed-in page renders inside `AppLayout` (header with hamburger `Sheet` nav on phones, offline banner, padded `<main>`); wide tables render as phone cards below `md` via `MobileCardList`/`DesktopOnly` (`frontend/src/components/ResponsiveList.tsx`) next to the desktop `<Table>`, so tests must scope queries with `within(screen.getByRole("table"))`; photos go through `prepareImageForUpload` (`frontend/src/lib/prepareImage.ts`) before upload. Phase 9+ (deployment, QA) is not implemented yet. Check the per-phase `Status:` lines in `docs/implementation-plan.md` for current status rather than assuming phase boundaries are clean.

## Commands

This is a Bun workspace monorepo (`backend/`, `frontend/`), not npm/yarn/pnpm.

```bash
bun install                # install all workspace deps, from repo root

bun run dev:backend < /dev/null &   # start the Express API with watch mode (http://localhost:4000)
bun run dev:frontend < /dev/null &  # start the React dev server with HMR (http://localhost:3000)

bun run dev:restart        # or: stop/start both in the background, logs to backend.log/frontend.log
bun run dev:restart --ngrok  # same, plus an ngrok tunnel to :3000 (restart alone never starts or stops ngrok)
bun run dev:stop           # stop both, plus the ngrok tunnel if running
```

Each can also be run directly from its own directory: `cd backend && bun run dev`.

- Health status: frontend at `http://localhost:3000`, backend healthcheck at `http://localhost:4000/api/health`.

- `frontend` has a `build` script (`vite build`, producing static output in `frontend/dist/`, including the `vite-plugin-pwa`-generated service worker/manifest); `backend` has no build step since Bun runs the TypeScript directly (`bun src/index.ts`).
- `bun run lint` / `bun run format` / `bun run format:check` (from repo root) run ESLint/Prettier across both workspaces via the root `eslint.config.mjs` and `.prettierrc.json`. `bun run typecheck` (from repo root) runs `tsc --noEmit` in `shared`, `backend`, and `frontend` — Vite and Bun strip types without checking them, so this is the only thing that catches type errors; keep it at 0. TypeScript is pinned to `~6.0` because `typescript-eslint` doesn't support TS 7 yet.
- **react-hook-form + zod typing**: the shared schemas transform values (`z.coerce`, `.default()`, `.transform()`), so a form's raw values (`z.input`) differ from the parsed result (`z.output`/`*Input` types). Let `useForm({ resolver: zodResolver(schema) })` infer both rather than passing one generic (`useForm<CreateCatInput>` doesn't typecheck). The shift report form is the exception — see `frontend/src/lib/shiftReportForm.ts` for why it uses the parsed type for both.
- `frontend` has Bun-native tests (`*.test.tsx`, using `@testing-library/react`) but no `test` script wired up yet — run with `cd frontend && bun test`.

## Architecture

- **Monorepo**: Bun workspaces defined in the root `package.json` (`backend`, `frontend`). A shared `tsconfig.base.json` at the root holds Bun's recommended compiler options; each workspace's `tsconfig.json` extends it.
- **Backend** (`backend/src/index.ts`): a plain Express app run directly by the Bun runtime — no transpile/build step, no nodemon (Bun's own `--watch` flag handles reload). CORS is enabled since the frontend calls it from a different origin/port in dev.
- **Database schema** (`backend/prisma/schema.prisma`): `snake_case` columns via explicit `@map` (native Postgres convention) with `camelCase` in the Prisma schema/client (Prisma/JS convention) — applies to every table, including the Better Auth ones. `bunx prisma generate` regenerates both the Prisma client (`src/generated/prisma`, gitignored) and `backend/prisma/ERD.md`, a Mermaid entity-relationship diagram of the full schema (via the `erd` generator block, `prisma-erd-generator`) — check it after any schema change instead of re-deriving relationships by reading models one by one.
- **Primary keys are not uniform on purpose**: the 14 Phase 1 domain tables (`Cat`, `Group`, `Litter`, `Kennel`, `ShiftReport`, `CatEntry`, `GroupEntryCatDetail`, `Photo`, `MeetAndGreet`, `KennelPrepChecklist`, `ChecklistAction`, `Announcement`, `SignTask`, `KennelMoveRequest`) use `Int @default(autoincrement())` IDs, while `User`/`Session`/`Account`/`Verification` keep Better Auth's `String` IDs. A foreign key from a Phase 1 table to `User` (e.g. `ShiftReport.authorId`) is therefore `String`; a foreign key between two Phase 1 tables is `Int`. Don't assume one or the other without checking — `ERD.md` shows the actual type per column.
- **Frontend** (`frontend/src/`): React + TypeScript, bundled and hot-reloaded by **Vite** (`frontend/vite.config.ts`) — `@vitejs/plugin-react` for Fast Refresh, `@tailwindcss/vite` for Tailwind v4, and `vite-plugin-pwa` for the installable-app manifest/service worker (`registerType: "prompt"`: `ReloadPrompt.tsx` registers it and asks before updating; `workbox-window` is a required dev dependency for that). Icons in `frontend/public/` are generated from `public/logo.png` by `bun run generate-pwa-assets` (`frontend/pwa-assets.config.ts`) and committed. The entrypoint is `frontend/index.html`, which loads `src/frontend.tsx`. Bun still runs the dev/build/test *commands* (`bun run dev` invokes the `vite` binary, `bun test` runs Bun's own test runner independently of Vite), but bundling itself is Vite's, not Bun's.
- The frontend calls the backend via an absolute URL from `PUBLIC_API_URL` in `frontend/.env`, exposed as `API_BASE` in `frontend/src/lib/config.ts`. Vite inlines `import.meta.env.PUBLIC_*` references into the browser bundle at build time (`envPrefix: "PUBLIC_"` in `vite.config.ts`), so changing the value needs a frontend restart/rebuild, and only `PUBLIC_`-prefixed vars ever reach the browser. There's no dev proxy configured, so CORS on the backend (`FRONTEND_URL`) is what makes this work locally.
- The backend and frontend aren't containerized; only Postgres is, via the root `docker-compose.yml` (`docker compose up -d postgres`), as an opt-in alternative to installing Postgres natively — see `docs/post-pull-checklist.md`. `docs/tech-stack.md` specifies Docker + a managed container platform for eventual production deployment, which is separate, later work (Phase 9).

## UI components & styling

- **Build UI from shadcn/ui components** in `frontend/src/components/ui/` (Radix base, Nova preset, Lucide icons — see `frontend/components.json`) rather than raw HTML controls: `Input`, `Textarea`, `NativeSelect`/`NativeSelectOption` (not raw `<select>`/`<option>`), `Checkbox`, `Label`, `Button`/`buttonVariants`, `Card`, `Alert` (wrapped by `ErrorAlert`), `Badge`, `Table`, `Dialog`, `AlertDialog`, `DropdownMenu`, `ToggleGroup`, `Collapsible`, `Skeleton`. Check that folder before writing a control by hand; add missing ones with `cd frontend && bunx shadcn@latest add <name>`.
- **After every `shadcn add`**, fix what the CLI gets wrong for this repo: it imports `cn` from the third-party `cn` npm package and re-adds that package to `frontend/package.json` — change the import to `../../lib/utils` (the existing `ui/` files use relative imports) and `bun remove cn`. Decline overwriting existing `ui/` components (they're customized), and `git diff` `src/index.css`/`src/lib/utils.ts` to make sure it didn't replace the brand theme or delete helpers (`init` once deleted `toDateTimeInputValue`). New field components should match `Input`'s look (`h-10`, `rounded-md`, `bg-white`, `focus-visible:ring-2`).
- **react-hook-form + Radix controls**: `Checkbox`, `ToggleGroup`, etc. are not native inputs, so `register()` doesn't work on them — use `<Controller>` (e.g. `checked={field.value === true}` / `onCheckedChange={(c) => field.onChange(c === true)}`). `Input`, `Textarea`, and `NativeSelect` are native and take `register()` directly. Collapsible form sections use `CollapsibleContent forceMount` plus a `hidden` class so collapsed fields stay mounted and keep their values.
- **Tailwind v4, CSS-first** — no `tailwind.config.js`. The theme lives in `frontend/src/index.css` in shadcn's standard layout: `@theme` holds the static brand palette (`navy`, `blue`, `cream`, `gray`, `gold`) and League Spartan font; `:root` holds the semantic CSS variables (`--primary`, `--background`, `--card`, `--muted`, `--destructive`, `--border`, `--radius`, …) defined in terms of the brand colors; `@theme inline` maps those variables onto utilities. To re-theme, edit `:root` (or paste a shadcn theme over it); dark mode would be a `.dark { … }` block overriding the same variables (`dark:` is class-based via `@custom-variant`, not OS preference). Use the tokens (`bg-primary`, `text-navy`, `border-input`) instead of hard-coded hex values; when a shadcn component needs a token that's missing, add the variable to `:root` and its mapping to `@theme inline`. `tw-animate-css` and `shadcn/tailwind.css` are imported for component animations and `data-open`/`data-checked`-style variants. Compose classes with `cn()` from `frontend/src/lib/utils.ts`.
- The `@/*` alias (→ `frontend/src/`) exists only because the shadcn CLI requires it; app code uses relative imports.
