## Problem

Lost Dog and Cat Rescue Foundation runs its day-to-day PetSmart adoption-site operations almost entirely over email. Shift reports, new-cat arrival announcements, adoption status updates, return-to-RCC notices, and kennel-prep instructions all arrive as separate, ad hoc email threads. There's no single place to check "what's the current state of this cat / this kennel" — the truth is scattered across whichever inbox happened to receive the most recent relevant email, formatted a little differently each time, and easy to lose track of as threads pile up. That fragmentation and lack of a central source of truth is the real problem; the shift report is just its biggest, most frequent example.

Volunteers work two-hour shifts (Morning, Mid-day, Evening) and currently submit a shift report by email at the end of each shift. A typical report covers:

- Kennels ready/reset for a new occupant
- Fecal scores
- Food intake (dry/wet, amount eaten)
- Medical notes
- Play group behavior/temperament notes
- Cleaning performed
- Nail trims
- Meet-and-greets
- Supplies used/restocked
- Other notes (e.g. adoption signage posted)
- Photos, attached to the email

Even though volunteers try to follow a shared format, every report ends up structured a little differently. This makes it cumbersome for the next shift, other volunteers, and staff to quickly find the information they need (open kennels, a specific cat's condition, what happened during a meet-and-greet). There is also no structured history of a given cat's condition or behavior over time — it's scattered across individual emails. Status changes (new arrivals, pending adoption, adopted, kennel resets) live inside free-text notes instead of being tracked as real state.

The same fragmentation shows up in the other email threads this project needs to address:

- New cat arrival announcements (name, age, sex, color/pattern, collar color, kennel — sometimes a pair arriving into the same kennel)
- Pending adoption / adopted announcements, sometimes including a scheduled pickup time
- Notifications that a cat is returning to the RCC (e.g. for observation) and is no longer at this location
- Kennel prep instructions ahead of an arrival or pickup, often chaining several actions together (e.g. "reset kennel 5, move Pepsi to kennel 5, then reset kennel 6")

Individually each of these threads is small, but together they add up to real operational cost: information that should be centralized and quickly scannable is instead spread across an inbox, inconsistently formatted, and easy to miss. They also all revolve around the same underlying state — a cat's status and a kennel's occupancy — which today lives only inside prose, nowhere structured.

## Solution

A mobile-first web app (PWA) that centralizes this operational information in one place instead of an inbox, starting with the shift report — the largest and most frequent source of email — and the related cat/kennel status threads, since they share the same underlying data. Volunteers use it on their phone to log a structured shift report in place of the email; volunteers and staff use it — on a phone or a computer — to look up recent reports and current cat/kennel status without searching through email threads and attachments.

This is the first iteration toward centralizing rescue-operations communication generally; MVP scope is deliberately limited to what's detailed in Features below, with the shift report as close to a 1:1 structured replacement of the email as possible, so the format is consistent and the data becomes usable (searchable, reportable, attributable to a specific cat over time) instead of just readable.

Two roles for MVP:
- **Volunteer** — create and edit their own shift reports.
- **Admin** — everything a Volunteer can do, plus edit/delete any report, manage the cat/kennel roster, post status changes and announcements, and manage user accounts.

## Features

### Shift reports
- One report per volunteer per shift, tagged with shift type (Morning / Mid-day / Evening) and date.
- **Split shift** — Morning and Evening shifts are sometimes split between two volunteers, who divide up the cats between them (the first volunteer picks which kitties they'll cover; the second covers the rest). A volunteer flags their report as a split shift and then only logs cat entries for the kitties they personally cared for. The two volunteers' reports aren't formally linked — each is just its own report for the same shift type + date, and a reader sees both were part of a split shift from the flag. There's no enforcement preventing the same cat from appearing in both reports; volunteers self-coordinate on who covers which cats. Shift-level fields (kennel status, cleaning, supplies, play, other notes) aren't split by cat — either volunteer can log any of them in their own report.
- **Kennel status** — the report lists every kennel with a Ready / Occupied / Needs Reset picker, laid out as a compact grid so it doesn't dominate the form; each one defaults to that kennel's current recorded state, so confirming "yes, still accurate" takes no extra action. Picking a different value than the system currently shows requires a short note explaining the mismatch (e.g. the roster says Ready but there's still a cat in there) — otherwise no note is needed. This is a **reporting tool only**: submitting it never changes the kennel's actual state or creates any announcement — it's for an Admin to review roster drift against what volunteers are actually seeing, not a way to reset a kennel (see Status & announcements below for how a kennel's real state changes).
- Repeatable cat entry within the report, one of two types:
  - **Individual entry** — fecal score, pee, pee/poo notes, food (dry amount + free-fed flag; wet amount + wet food brand, defaulting to Hill's and only requiring a pick when it's different), snack/treat (Churu, Greenies, other + note), food notes, medical section (general medical notes, plus a "dewormer given" action when one is due, and a "probiotic given" checkbox on any shift's entries when the cat needs a probiotic), behavior notes, other notes (catch-all for anything about the cat that doesn't fit the fields above), nail trim flag, photo(s).
  - **Group entry** — for cats housed/fostered together (e.g. "Sprite/Pepsi/Nehi"), since some things can't be attributed to one cat in the group:
    - Shared across the group: fecal score, pee, pee/poo notes, dry food amount, water, food notes (for the shared dry food/water), other notes (catch-all for the group). (Dry food is always the same brand, so brand isn't tracked for dry.)
    - Individual per cat in the group: wet food amount + brand (default Hill's), snack/treat, food notes (for that cat's wet food/treats), medical section (notes + dewormer given + probiotic given, any shift), behavior notes, other notes (catch-all for that cat), nail trim flag, photo(s).
- A cat entry's medical section flags when a dewormer is due, with its due date (see Cat & kennel roster below); marking it "given" during a shift clears the flag. Dewormer is a one-time treatment — once given, there's no recurring schedule to track (the due date that got it there stays as a historical record, but is no longer acted on).
- A cat entry's medical section also shows a "probiotic given" checkbox when the cat has an Admin-set "needs probiotic" flag (see Cat & kennel roster below) — on any shift's entry (Morning, Mid-day, or Evening), since a probiotic dose can be given as part of whichever shift covers the cat that day, not just Evening. Checking it just logs that dose (its date and shift, same precision as everything else in a shift report — no separate timestamp) — unlike dewormer, it does not clear the flag, since a cat with diarrhea typically needs a probiotic over several consecutive days. Only an Admin clears "needs probiotic," once the diarrhea has resolved.
- Shift-level fields (not tied to one cat): cleaning performed, supplies restocked, general "other" notes (for anything not about a specific cat — cat-specific miscellany goes in that cat entry's other notes).
- **Play** — a shift-level section for play notes that aren't specific to one cat (e.g. a play group session, which cats played well together). Free text, optionally tagged with the cats involved (picked from the active roster); a tagged play note shows up in each tagged cat's report history. Individual behavior still goes in each cat entry's behavior notes.
- Announcement-driven action items — posting/removing an adoption sign, confirming a pickup, completing a kennel move, working through a kennel-prep task list — are **not** part of the shift report. They're completed from the Announcements page instead (see Status & announcements below), so the shift report stays a narrative/roster record rather than a to-do list.
- Repeatable meet-and-greet entry: one or more cats (a family may meet more than one cat in a visit) + a free-text note on context/outcome. Multiple meet-and-greets can be logged in one shift.
- Fecal score and food amount use structured pickers (fecal score: 1–7 scale, plus a "none" option for when there was no bowel movement to score during the shift; food amount: none/some/all + free-fed flag), with the dedicated pee/poo notes and food notes fields for anything unusual — keeps data consistent while still allowing detail.
- Pee is a simple yes/none flag — whether the cat (or, for a group entry, the group) was seen to urinate during the shift. No quality scale like fecal score, just presence.
- Photos uploaded inside a cat entry (individual, or per-cat within a group) are automatically tagged with that cat.
- A report-level **Photos** section for photos that aren't logged against a specific cat entry. Each photo there can be tagged with zero or more cats (picked from the active roster; e.g. a group shot tagged with every cat in it) or left **unassigned**.
- A photo's cat tags can be added, changed, or removed after upload — by the photo's uploader or any Admin — for both report-level and cat-entry photos, including after the report has been submitted. This is how unassigned photos get tagged later.

### Roles & permissions
- **Volunteer**: create/edit own reports only — cannot delete their own reports; only an Admin can delete a report. Can add/change/remove cat tags on photos they uploaded. Can view photos but not download them. From the Announcements page, can complete any open action item — checking off a sign task, a kennel move, a kennel-prep step, or confirming a cat's pickup (the one status change a Volunteer can make, alongside an Admin, since a Volunteer is usually the one present when it happens). Can also leave a free-text comment on any announcement.
- **Admin**: edit/delete any report; add/change/remove cat tags on any photo; download photos (single or bulk zip); manage the cat/kennel roster (add cats, assign kennels, intake); post status changes and announcements, including free-form ad-hoc ones with their own task lists (the only announcement types an Admin can edit or delete); create and manage volunteer/admin user accounts; view the Cat/Kennel activity history (see Reporting/lookup below).
- Self-registration is disabled — an Admin creates every user account (Volunteer or Admin) directly; there is no public sign-up flow.
- Deleting a user is a soft delete: an Admin can delete a Volunteer or Admin who has left, which blocks that user from logging in but keeps their account and past shift reports intact (still fully viewable/attributed to them). It is not a destructive/permanent delete.
- No roles beyond Volunteer/Admin in MVP — anyone with in-app access is one or the other; people outside those roles (e.g. fosters, front-desk staff) who need visibility are reached via the existing Google Group email notifications, not in-app accounts.

### Cat & kennel roster
- Persistent cat profile that shift reports reference, instead of free-typing a cat's name each time — avoids inconsistency (e.g. name spelling/aliases) and enables per-cat history and reporting.
- New-arrival intake captures: name, age (years and months), sex, color/pattern (a picklist of common values, e.g. Black, Calico, Tuxedo, Siamese, Seal Point — with an "Other" option for anything not listed, since real cats don't always fit a fixed set), collar color, microchip number (optional), kennel assignment, and whether a dewormer is due, with a due date (known at intake from the cat's existing paper notebook). Two cats can arrive together into the same kennel (modeled the same way as a shift-report group).
- Kennel tracks its current occupant(s) (single cat or group) and ready/reset state, plus a 4th state, **`planned`** — a plain Admin-settable label meaning "earmarked for an incoming arrival, nobody's here yet," with no linked data (not tied to a specific cat/date); purely a heads-up note on the roster, the same way the other three states are just labels.
- A cat's dewormer status is visible on its profile/roster entry, replacing the current binder lookup volunteers do before each shift, and includes the due date the notebook recorded — a cat still `due` past that date shows as **Overdue** rather than just `Due`, so it stands out without anyone checking dates by hand. Marking it given (from a shift report or the cat's profile) clears the flag for good — it's a one-time treatment, not a recurring schedule (the due date stays as a historical record once given).
- A cat's "needs probiotic" status is also visible on its profile/roster entry, but unlike dewormer it isn't set at intake: an Admin manually flags a cat as needing a probiotic after a volunteer reports diarrhea (via a shift report's fecal score or medical notes). Once flagged, every shift report shows a "probiotic given" checkbox for that cat (not just Evening — see Shift reports above) until an Admin manually clears the flag — checking the box logs that dose but doesn't end the need, since a probiotic is typically given over several consecutive days while the diarrhea resolves.
- While a cat's "needs probiotic" flag is set, its roster entry shows an **Overdue** indicator (same pattern as the dewormer Overdue badge above) once 24 hours have passed since its last logged dose with no new one — derived from the most recent shift-report entry with "probiotic given" checked for that cat, not a separately tracked record. If no dose has ever been logged since the flag was set, it's overdue from the moment the flag was set.
- **Bonded pair** — an Admin can flag a Group as `bonded`, meaning the two cats in it are a bonded pair that should always be kept together in the same kennel (as opposed to a Group that's just co-housed for other reasons, e.g. temporary fostering). Bonded is always pairwise — it can only be set on a Group of exactly two Cats — and is informational only in MVP: the app doesn't block an Admin from splitting a bonded Group across kennels, it's just a visible note on the roster (e.g. so an Admin knows to re-pair them, or knows not to split them, when reassigning kennels).
- **Siblings** — an Admin can tag two or more Cats as siblings (litter-mates) at or after intake. Unlike a bonded pair, siblings don't necessarily share a kennel or a Group — it's purely informational, shown on each sibling's profile/roster entry regardless of their current kennel assignment, so volunteers/Admins know cats in different kennels are related (e.g. for meet-and-greet or adoption conversations). A cat can be both part of a bonded Group and tagged with siblings at the same time — the two are independent.

### Status & announcements
Replaces the other ad hoc email threads (new-cat, adoption, sick-return, kennel-prep) with structured, in-app notifications tied to the cat/kennel roster, all surfaced and acted on from a single Announcements page — not the shift report (see Shift reports above).
- Cat status field (`available` → `pending adoption` → `adopted` → `picked up`), updated by Admins. A cat is `available` as soon as it's added to the roster — there's no separate "new arrival" status, just an announcement posted at intake. The adoption process is sometimes fast enough that there's no separate pending period — an Admin can move a cat directly from `available` to `adopted`, skipping `pending adoption` entirely. Both `pending adoption` **and** `adopted` can revert back to `available` if an application falls through (e.g. it doesn't work out — including after the paperwork's done but before pickup) — this posts a new "back available" announcement and resolves the earlier pending-adoption/adopted one. Status changes are always a manual Admin action — a meet-and-greet outcome is logged as a note only and never automatically changes a cat's status — **except** `adopted` → `picked up`, which a Volunteer can also trigger (see Confirm pickup below), since a Volunteer is usually the one physically present when the adopter arrives, not an Admin at a desk.
- `adopted` means the paperwork/application is done; `picked up` is the separate, later moment the adopter actually takes the cat home. Transitioning to `picked up` marks the cat's kennel `needs reset` (same trigger as Returned to RCC — see Kennel needs reset below) and resolves the pending-adoption/adopted Announcement.
- **Confirm pickup** — an action on the Announcements page (not the shift report) for every cat that's `adopted` with a scheduled pickup date/time (see the Cat entity in Data model below). Any Volunteer or Admin can complete it, which transitions that cat to `picked up`, marks its kennel `needs reset`, and resolves the announcement — recording who and when. Only shown once a pickup is scheduled.
- **Adoption sign tasks** — there's a different kennel sign for Adoption Pending and Adopted. Each status change automatically creates a sign task that appears as a completable action on that cat's Pending Adoption / Adopted announcement on the Announcements page until it's checked off:
  - → `pending adoption`: post the Adoption Pending sign.
  - → `adopted`: post the Adopted sign (replacing the Adoption Pending sign) — whether arriving from `pending adoption` or directly from `available` (the fast-track path). On the fast-track path there's no Adoption Pending sign to consider at all, since one was never posted.
  - → back to `available` (fallthrough from `pending adoption`): remove the Adoption Pending sign.
  - → back to `available` (fallthrough from `adopted`): remove the Adopted sign. Unlike the normal `adopted` → `picked up` path (see below), the cat isn't leaving its kennel here, so there's no kennel-reset event to hang the sign removal on — this is its own remove-sign task instead.
  - A new status change (or Returned to RCC) cancels any still-open sign task for that cat, so volunteers never see a stale task — e.g. if a cat goes pending → adopted before the Pending sign was posted, the Pending task is cancelled and only the Adopted task remains. A remove-sign task is only created if a sign was actually posted: a fallthrough before the Pending or Adopted sign went up just cancels that task, and Returned to RCC creates a remove-sign task only if a sign is currently posted.
  - No separate task for taking down the Adopted sign when it comes down via `picked up` — removing it there is part of resetting the kennel after pickup (see Kennel below). A fallthrough from `adopted` is the one case where taking the Adopted sign down *is* its own remove-sign task, per above.
  - Sign tasks are created only by the system from Admin status changes; volunteers can't create them, but any Volunteer or Admin can complete one from the Announcements page.
- **Returned to RCC** is an action, not an ongoing status: it removes the cat from the active roster entirely (no further tracking at this location — if it comes back later it's re-entered like a new arrival) and marks its kennel `needs reset` (see Kennel needs reset below). An optional free-text reason (e.g. "for observation") can be logged for the record, but volunteers only see that the kennel needs a reset, not the reason.
- **Kennel needs reset** — whenever a kennel is vacated (a confirmed pickup, a cat returned to RCC, a completed kennel move, an Admin reassigning or deleting a cat, or a group changing membership), the app posts a "kennel needs reset" announcement with a single "reset kennel" action. Completing it (any Volunteer or Admin, from the Announcements page) marks the kennel `ready` again and resolves the announcement — this is the only thing that changes a kennel back to `ready` after use; the shift report's own kennel-status section (see Shift reports above) is a separate, non-mutating report and never does this.
- Announcement types, visible to all volunteers, separate from a shift report:
  - New cat arrival
  - Pending adoption / adopted (with pickup date/time when scheduled) / back available (after a fallthrough)
  - Cat returned to RCC (no reason shown; the kennel's own reset need is its own separate "Kennel needs reset" announcement, below)
  - Kennel needs reset
  - Kennel move requested
  - Ad-hoc / manual (see below)
- **Kennel prep checklist** — an Admin posts an ad-hoc announcement (see below) with an ordered list of steps, each one of three kinds: a plain text task (just a checkbox, for anything not tied to a kennel or cat — e.g. "sweep the floor"), reset a kennel, or move a cat/group into a kennel — e.g. "reset kennel 5 → move Pepsi to kennel 5 → reset kennel 6." There's no separate checklist-creation flow — it's the same "New Announcement" form used for any ad-hoc post, just with one or more steps attached. Any Volunteer or Admin checks steps off from the Announcements page, strictly in order — only the next incomplete step can be marked done. A "move cat into a kennel" step only moves that cat/group — it does **not** automatically flag the cat's previous kennel as needing reset; if that's needed (as in the example, where kennel 6 is Pepsi's old spot), the Admin adds it as its own explicit step, same as any other reset step. This is different from a Kennel move request below, which has no sequence to place a reset step into and so handles it automatically. The announcement resolves automatically once every step is checked off.
- **Kennel move request** — an Admin can request moving a Cat or Group to a different kennel, independent of a kennel prep checklist (e.g. reshuffling, reuniting a bonded pair, freeing up a kennel). Unlike a checklist, this is a single standalone action, not an ordered sequence. It appears as a completable action on its own announcement on the Announcements page until a Volunteer or Admin checks it off, which performs the move (updates the Cat/Group's kennel) and marks the vacated kennel `needs reset` (see Kennel needs reset above) **automatically**, since there's no explicit-step mechanism to declare it otherwise. Creating a request posts a new announcement; completing it resolves that announcement.
- **Ad-hoc / manual announcements** — an Admin can post a free-form announcement at any time from the Announcements page: a title, and either a message, one or more ordered steps (see Kennel prep checklist above), or both. An announcement with steps resolves automatically once every step is done; a message-only one stays open until an Admin explicitly marks it resolved. An Admin can edit a manual announcement's title/message (its steps, once posted, aren't editable — only completable) or delete it outright, e.g. if posted by mistake. These are the only announcements an Admin can edit or delete — every system-generated type is read-only apart from completing its action.
- **Comments** — any Volunteer or Admin can leave one free-text comment on any announcement, of any type, as a running note (e.g. "called the family, pickup moved to Friday") — separate from a manual announcement's own message, and overwritten (not threaded) each time it's edited.
- **Filtering & sorting** — the Announcements page defaults to the last 7 days, with an adjustable date range and an "active only" toggle (announcements with an open action) that combine, e.g. widen the range to see resolved history, or turn on active-only with an all-time range to see every still-open item regardless of age. Every column (type, cat, kennel, created date, closed date, status) is sortable.
- **Audit trail** — every resolution, system-generated or manual, records who resolved it and when, shown alongside the announcement's creation date. No automatic long-term expiration/purging of announcements in MVP (deferred — see Out of scope).

### Reporting / lookup
- View/search past shift reports by cat, date, or kennel, so the next shift can catch up without reading an email chain.
- View a single cat's report history in one place (fecal/pee/food and their notes, behavior, medical, other notes, meet-and-greets, tagged play notes, and tagged photos over recent shifts).
- **Photo browse** view across all shift reports, newest first, with two filters:
  - **By cat** — every photo tagged with that cat, from cat entries or the report-level Photos section. Inactive cats (returned to RCC) remain selectable, same as report history.
  - **Unassigned** — photos with no cat tags, so they can be found and tagged.
  - Each photo links back to its shift report (date, shift type, uploader), and the uploader or an Admin can edit its tags inline from this view.
  - **Download (Admin only)** — an Admin can download any single photo at its original full resolution, or download every photo matching the current filter (a cat, or unassigned) as a single zip. Downloaded files are named for easy identification: date, shift type, and tagged cat name(s), or "unassigned". Volunteers can view photos in the app but not download them.
- **Cat & Kennel activity history (Admin only)** — every create, edit, and delete on a Cat or a Kennel is recorded (who, when, what changed), viewable as an audit trail — e.g. "kennel 3: Admin X moved Pepsi in, Sept 20," "kennel 3: Admin Y changed state to needs reset, Sept 22." This is a debugging/accountability tool for Admins, not a volunteer-facing feature, and is separate from the Announcement feed (which is about a handful of structured, volunteer-relevant status events) and from shift-report-derived per-cat history above (which is about a cat's condition/care, not roster edits). Backed by a generic activity-log record (entity type, entity id, action, actor, timestamp, description) so later entities (Group, Litter, etc.) can reuse the same mechanism rather than each getting a bespoke history table.

### Email notifications
Sent to the existing Google Group already used for these communications today (not per-user addresses), individually per event (not batched), for:
- New cat arrival
- Status change to pending adoption / adopted (including a scheduled pickup date/time, when set)
- Back available (after a pending adoption falls through)
- Returned to RCC
- Kennel needs reset
- A new ad-hoc announcement posted (including one with a kennel-prep task list)
- A new kennel move requested
- Shift report submitted — a full outline of the completed report (all cat/group entries with their fields, shift-level fields, and any meet-and-greets), mirroring the in-app report's content in plain text. Uploaded photos are not included in the email; viewing them requires opening the app.

All eight notification types go to the same single existing Google Group. Whoever is a member of the Google Group receives these — membership, not an in-app preference, is what controls who gets notified for MVP. Group membership is managed entirely outside the app (in Google Groups/Workspace admin); the app just sends to the group address and doesn't need to read or display who's in it. The email contains the full detail of the event — for the seven announcement types, same as the in-app announcement; for a submitted shift report, a full outline of the report as described above. A split-shift report triggers its own email covering just the cats that volunteer logged. No push notifications, and no per-user opt-in/opt-out, in MVP.

## Data model / entities

- **User** — name, email, role (`Volunteer` | `Admin`), password (credential-based auth), soft-delete timestamp (a deleted user cannot log in, but their account and past reports remain intact). Created only by an Admin — no self-registration.

- **Cat** — name, age at intake (years and months), sex, color/pattern (a picklist of common values plus free-text "Other"), collar color, microchip number (optional — not every cat is chipped at intake; not unique across records, since a re-admitted cat is entered again as a new Cat), current kennel or group, status (`available` | `pending adoption` | `adopted` | `picked up` — a cat is `available` as soon as it's added to the roster, no separate "new arrival" status; `available` can go directly to `adopted`, skipping `pending adoption`, when the process moves fast; both `pending adoption` and `adopted` can revert to `available` on a fallthrough; `adopted` → `picked up` is the one status change a Volunteer can also make, via Confirm pickup, not just an Admin), scheduled pickup date/time (optional, set/edited any time while pending adoption/adopted, not only at the moment of transition; cleared on a fallthrough to available), pickup attribution (who confirmed the pickup and when — same shape as a SignTask's or KennelMoveRequest's completion fields, set only by Confirm pickup), dewormer status (`due` | `given`, set at intake from the cat's existing paper notebook; one-time, no recurring schedule) with an associated due date (also set at intake; drives an "Overdue" indicator once passed while still `due`, and is kept as a historical record once `given`), needs-probiotic flag (boolean, set manually by an Admin after diarrhea is reported — not tied to intake — and cleared manually by an Admin once resolved; unlike dewormer it is not cleared by logging a dose; while set, drives its own "Overdue" indicator once 24h pass without a newly logged dose, derived from CatEntry/GroupEntryCatDetail history rather than a separate tracked record), litter reference (optional, see Litter below), active flag. Set inactive (not deleted) when returned to RCC, with an optional Admin-only reason note; a re-admitted cat is entered again like a new arrival rather than reactivated. Past shift reports referencing an inactive cat remain fully viewable in history/search — going inactive removes it from the active roster, not from the record.

- **Group** — a set of Cats housed/fostered together (e.g. "Sprite/Pepsi/Nehi"); shares one kennel and is the target of shared fields on a shift report entry. Used both for arrivals (a pair intake into one kennel) and shift reporting. Bonded flag (boolean, Admin-set) — true means the two Cats in this Group are a bonded pair that should always stay in the same kennel; only settable when the Group has exactly two Cats, since bonded is always pairwise. Bonded is informational only in MVP — not enforced against kennel/Group reassignment. When a Cat leaves a Group (adopted or returned to RCC), it's removed from the Group; if only one Cat remains, the Group dissolves and that Cat becomes an Individual in the shared kennel, otherwise the remaining Cats stay a (smaller) Group — a dissolved/resized Group that was bonded loses the bonded flag, since bonded no longer applies once the pair is broken up.

- **Litter** — a set of two or more Cats tagged by an Admin as siblings, at or after intake. Independent of Group/kennel — sibling Cats may or may not currently share a kennel or Group, and moving a Cat between kennels/Groups doesn't affect its Litter membership. Purely informational: shown on each member Cat's profile/roster entry so volunteers/Admins can see who's related regardless of current housing.

- **Kennel** — number, current occupant (a Cat, a Group, or empty), state (`occupied` | `needs reset` | `ready` | `planned`). Resetting a kennel includes taking down any Adopted sign on it. State is driven by roster events (a Cat/Group assigned → `occupied`; vacated, via a confirmed pickup, return to RCC, a completed kennel move, or an Admin reassigning/removing a cat or group → `needs reset`, each posting a "kennel needs reset" announcement) or an Admin's direct edit; completing that announcement's action (any Volunteer or Admin, from the Announcements page) sets it back to `ready`. A volunteer's shift-report kennel status entry (per Shift reports above) is a separate, non-mutating report of what they observed and never changes this field directly. `planned` is the exception to all of that — a plain Admin-set label ("earmarked for an incoming arrival, nobody's here yet") with no linked data and no automatic transition into or out of it.

- **ShiftReport** — author (User), shift type (`Morning` | `Mid-day` | `Evening`), date, split-shift flag (boolean; Morning/Evening only — no formal link to the other volunteer's report, just a marker that this report only covers a subset of the shift's cats), a per-kennel status report (every kennel's reported state — `ready`/`occupied`/`needs reset` — plus a note, required only when it conflicts with the kennel's actual current state; purely observational, see Shift reports above), cleaning notes, supplies notes, other notes, play notes + tagged Cats (zero or more, many-to-many), report-level Photos (see Photo below), created/edited timestamps. Editable only by its author, or by an Admin. Sign tasks, kennel move requests, kennel-prep steps, and pickup confirmations are all completed from the Announcements page and aren't tied to any specific ShiftReport (a Cat's pickup attribution is just `pickedUpById`/`pickedUpAt`, with no report reference).

- **CatEntry** — belongs to a ShiftReport; references either one Cat (individual) or one Group.
  - Individual: fecal score, pee flag, pee/poo notes, dry food amount + free-fed flag, wet food amount + brand (default Hill's), snack/treat, food notes, medical notes, dewormer-given flag (only relevant while the Cat's dewormer status is `due`), probiotic-given flag (shown on any shift's entry while the Cat's needs-probiotic flag is set — logging it does not clear that flag), behavior notes, other notes (catch-all), nail trim flag, photo(s) (Photo records auto-tagged with the entry's Cat).
  - Group: fecal score, pee flag, pee/poo notes, dry food amount, water, food notes, and other notes logged once for the group (dry food brand is not tracked — always the same); wet food amount + brand, snack/treat, food notes, medical notes, dewormer-given flag, probiotic-given flag (any shift, per Cat in the group), behavior notes, other notes, nail trim flag, and photo(s) logged per Cat within the group (Photo records auto-tagged with that specific Cat).

- **Photo** — belongs to a ShiftReport; uploaded by a User; storage reference (object key in S3-compatible storage — the binary isn't stored in Postgres, per `Tech-Stack.md`); uploaded-at timestamp; optional CatEntry reference (set when uploaded inside a cat entry, empty for report-level photos); tagged Cats (zero or more, many-to-many). A photo with no tagged Cats is **unassigned**. Tags are editable after upload by the uploader or an Admin; a cat-entry photo starts tagged with its entry's Cat but can be retagged like any other. Photos tagged with an inactive Cat stay tagged and viewable. The original full-resolution file is always kept in storage (any resized/compressed copies for in-app viewing are in addition to it, not a replacement), so Admins can download the original; downloading is Admin-only.

- **MeetAndGreet** — belongs to a ShiftReport; references one or more Cats, plus a free-text note on context/outcome. Surfaces on each referenced Cat's report history.

- **KennelPrepChecklist** — created by an Admin as part of posting an ad-hoc announcement (see Status & announcements above); an ordered list of **ChecklistAction**s, each one of `reset kennel` | `move cat to kennel` | `plain text task` (target Kennel and/or target Cat/Group when applicable, a free-text description for a plain text task, completed flag, completed by/at). Any Volunteer or Admin checks actions off from the Announcements page, strictly in order — only the next incomplete action can be marked done.

- **Announcement** — type (`new arrival` | `pending adoption` | `adopted` | `back available` | `returned to RCC` | `kennel move requested` | `kennel needs reset` | `manual`), reference to the related Cat/Kennel/Checklist, title and message (`manual` only — a checklist-only manual announcement can omit the message), created-by (`manual` only), resolved flag with resolved-at/resolved-by (set on every resolution, system or manual, for an audit trail), a free-text comment any Volunteer or Admin can add/edit (separate from a manual announcement's own message), and whether a notification email was sent for it. `new arrival` never resolves; `back available` and `returned to RCC` resolve via their remove-sign SignTask if one was created, otherwise never resolve; `pending adoption`/`adopted` resolve together at Confirm pickup; `kennel move requested` resolves when its request is done or cancelled; `kennel needs reset` resolves when its reset action is completed; `manual` resolves automatically once every attached checklist step is done, or must be marked resolved manually by an Admin if it has no steps. The Announcements page filters by an adjustable date range (default last 7 days) and an "active only" toggle rather than a fixed 24-hour window, and every column is sortable.

- **SignTask** — auto-created when a Cat's status changes (not user-created): Cat, Kennel at time of creation, action (`post pending` | `post adopted` | `remove pending` | `remove adopted`), triggering Announcement, state (`open` | `done` | `cancelled`), completed by (User) / completed at. Open tasks appear as a completable action on their announcement on the Announcements page until done; a later status change or Returned to RCC cancels any open task for that Cat. Any Volunteer or Admin can complete one — not tied to any specific ShiftReport.

- **KennelMoveRequest** — created by an Admin (not auto-created), independent of a KennelPrepChecklist: references one Cat or Group (the occupant to move), the source Kennel (captured at creation time, like SignTask's kennel snapshot) and destination Kennel, an optional reason note, state (`open` | `done` | `cancelled`), completed by (User) / completed at, and the Announcement it triggered. Open requests appear as a completable action on their announcement on the Announcements page until done — not tied to any specific ShiftReport. Completing it moves the Cat/Group to the destination Kennel and marks the source Kennel `needs reset`.

- **ActivityLog** — a generic audit-trail record, one row per create/edit/delete on a tracked entity: entity type (`Cat` | `Kennel`, extensible to others later), entity id, action (`create` | `update` | `delete`), actor (User), timestamp, and a description of what changed. Written automatically by the Cat and Kennel routes on every mutation — not user-created, and (per Announcement/SignTask/etc.) not something a Volunteer can see or write to. Admin-only, viewable as a per-cat or per-kennel history list. See Reporting/lookup above.

## Platform

Mobile-first web app (PWA) — installable to the home screen, works in the phone browser, no app-store submission required. The first release is also fully usable in a desktop/laptop web browser: the same app and features at every screen size, with a responsive layout that makes use of the wider screen on a computer (e.g. roster grid, report search, photo browse) rather than a stretched phone layout. On a computer, photo upload uses a normal file picker instead of the phone camera. Fastest path to MVP and easiest to iterate on; a native app can be revisited later if offline support or app-store presence becomes a priority.

Scoped to a single site (one PetSmart location) for MVP — one kennel-numbering scheme, no Site entity. Multi-site support is a backlog item if the rescue expands to satellite locations.

## Design / Branding

The app's visual design mirrors the Lost Dog & Cat Rescue Foundation website (lostdogrescue.org) for brand consistency. This means adopting the site's color palette, typography, and button styling in the app's own mobile-first, responsive UI (phone and computer) — not a literal clone of the marketing site's layout or imagery, since the app is a utilitarian internal tool (shift reports, roster, checklists) rather than a public-facing page.

- **Colors**: navy (`#001F70`, headings/nav), blue (`#0C4AC5`, primary buttons/links), cream/off-white (`#F6F5F4`, background), gray (`#62646A`, body text), plus the site's gold/yellow as an accent color (underlines, highlights, badges).
- **Typography**: League Spartan (Google Font), matching the site's font throughout.
- **Buttons**: fully rounded pill shape, matching the site's button style.
- **Logo**: the app header reuses the organization's actual logo/wordmark (the navy shield mark) rather than a generic app icon. This needs the source logo asset from the organization, using their standard mark rather than the site's "25 years" anniversary ribbon variant, since that's tied to a specific anniversary and not evergreen.

This is a design decision only for now — actual theme/CSS implementation happens once feature UI work begins; the current code is still the Phase 0 skeleton with no feature UI built yet (see `CLAUDE.md`).

## Out of scope for MVP (backlog)

- Native iOS/Android apps
- Full adoption application intake/CRM (meet-and-greets are logged as a simple cats + note entry, not a full workflow)
- Push notifications (MVP uses email instead)
- Per-user notification preferences (opt-in/opt-out) — MVP sends to the existing Google Group for everyone; individual control is a future enhancement
- Per-shift-targeted notifications (e.g. only notify the next shift) — MVP notifies the whole Google Group
- Digest/batched emails — MVP sends one email per event
- Long-term announcement expiration/purging (e.g. a hard 3-week cutoff) — MVP's Announcements page just offers an adjustable date-range filter (defaulting to the last 7 days) plus an "active only" toggle, with no automatic deletion
- Advanced analytics/dashboards beyond basic report lookup and per-cat history
- Offline mode
- Structured end-of-shift checklist (e.g. cleaning tasks, "check locks before leaving") — MVP keeps cleaning as a free-text field on the shift report
- A standing list of reminders/guidelines shown to volunteers (e.g. "no toys in the kennel") — not part of MVP's shift-report flow
- Multi-site support (Site entity, per-site kennel numbering) — MVP assumes a single location
- A fallback shift-report path for volunteers without a smartphone — MVP assumes all active volunteers can access the PWA on a phone browser
